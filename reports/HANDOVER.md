## 4. 데이터 계약 v1.2 (최종 확정 — 양측 합의 + 사장 결정 반영)

전문은 `report-api.md`. 요약:

- **모든 응답**: 성공 `{ ok: true, data }` / 실패 `{ ok: false, error: { code, message } }` — `message`는 쉬운 한국어, 화면에 그대로 표시 가능
- **`GET /api/draw`** (최신) / **`?round=N`** (특정): `data = { round, date "YYYY-MM-DD", numbers[6] 오름차순, bonus, firstPrize: { winners, amountPerWinner(원) } }`
- **`GET /api/stats`**: `data = { latestRound, frequency[45]{number,count}, oddEven{odd,even}, mostFrequent[3], leastFrequent[3] }`
- **상태코드**: 200 / 400 `INVALID_ROUND` / 404 `NOT_FOUND` / 405 / 500 / 502 `UPSTREAM_ERROR`
- **동률 규칙**: 자주/드문 번호가 동률이면 **낮은 번호 우선 — 서버만 계산**한다. 프론트는 절대 재계산하지 않는다 (실데이터 22·32번 동률에서 어긋난 전례 있음 — 검수 6차).
- **등수 계산은 프론트**: 6개=1등 / 5개+보너스=2등 / 5개=3등 / 4개=4등 / 3개=5등 / 그 외 낙첨

## 5. 핵심 설계 결정과 이유 (결정 로그)

| 결정 | 내용 · 이유 |

| 스냅샷 파일 (사장 승인) | 과거 회차는 불변이라 파일로 포함. 없으면 통계마다 동행복권에 124번 요청해야 함. 오래돼도 서버가 부족분을 실시간 보충 → **방치해도 항상 최신** |
| 동행복권 신주소 | 옛 공개 API는 2026 개편으로 사라짐. 현재: `/lt645/selectPstLt645InfoNew.do?srchDir=center&srchLtEpsd=N` (10회차 묶음). **또 바뀌면 `api/_lib/dhlottery.js` 한 파일만 고치면 됨** — 그동안 사이트는 502 + 친절한 안내로 동작 |

| 사장 결정 모음 | 자주/드문 **3개씩** · 통계에 보너스 **미포함** · 1등 당첨금 **표시**(0명이면 "1등 당첨자 없음") · 고정 6개 꽉 차면 새 번호는 **바로 제외** · 미입력 시 **안내 문구** · picker 문구 "한 번 누르면 고정…" |

## 6. 운영 — 평소에 할 일과 문제 시 대처

- **평소**: 없음. 토요일 새 회차는 자동 반영(추첨 후 최대 ~1시간).
- **배포**: `git push`만 하면 Vercel이 자동 재배포. 배포 전 권장: 스냅샷 재생성(`node api/_scripts/build-snapshot.js`). 전체 체크리스트는 `report-api.md` "배포 직전 체크리스트".
- **사이트가 로그인으로 튕기면**: Vercel 대시보드 → Settings → Deployment Protection 확인 (첫 배포 때 겪음 — 코드 문제 아님).
- **데이터가 안 나오면**: ① `/api/draw`를 직접 열어 에러 확인 → ② 502면 동행복권 개편 가능성 → `api/_lib/dhlottery.js`의 주소·응답 필드 확인.
- **검증 도구**: `node app/test/local-server.js 8899` → 화면+함수 통합 실행 / `node app/test/test-lottery.js` → 순수 로직 21건 / `node app/test/browser-test.js` → 헤드리스 크롬 화면 검증.

## 7. 일하는 방식 (전 터미널)

1. **작업 시작 전에 `reports/`를 전부 읽는다.** (프론트가 로직의 확정 계약을 안 읽어서 이중 계약이 생겼던 사고 — 검수 6차 — 재발 금지)
2. 작업이 끝나면 자기 보고서(`report-front.md`/`report-api.md`)에 **한 일 / 확인한 것 / 막힌 것**을 남긴다. "확인함"에는 재현 가능한 근거(테스트·스크린샷)를 붙인다.
3. 관리 터미널이 `review.md`로 검수한다 — 통과/수정필요. 수정 지적은 반영하고 보고서에 기록한다.
4. 계약(데이터 모양)을 바꾸고 싶으면 코드로 우회하지 말고 보고서에 질문을 남긴다. 합의 없는 계약 변경 금지.
5. 사장 결정이 필요한 것(규칙 변경, 루트 파일, 합의사항 변경)은 먼저 묻는다.
