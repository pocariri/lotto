## 함수와 응답 모양 (JSON 계약 v1.2 — 확정, 구현 완료)

### 공통 규칙

- 모든 응답은 JSON. 성공/실패를 겉봉투로 구분한다.

```jsonc
// 성공
{ "ok": true, "data": { ... } }

// 실패
{ "ok": false, "error": { "code": "NOT_FOUND", "message": "1200회는 아직 추첨 전이에요." } }
```

- HTTP 상태코드: 성공 `200` / 잘못된 요청(회차가 숫자가 아님 등) `400` + code `INVALID_ROUND` / 없는·아직 안 나온 회차 `404` + code `NOT_FOUND` / GET이 아닌 호출 `405` + code `METHOD_NOT_ALLOWED` / 서버 내부 오류 `500` + code `INTERNAL_ERROR` / 동행복권 연결 실패 `502` + code `UPSTREAM_ERROR`.
- 프론트는 `ok`가 `false`면 `error.message`를 그대로 사용자에게 보여줘도 되게, 메시지는 항상 쉬운 한국어로 준다.
- 번호 배열은 **항상 오름차순 정렬**해서 준다. 날짜는 `"YYYY-MM-DD"` 문자열.

### 함수 1 — `GET /api/draw` (회차 당첨번호 조회)

- `GET /api/draw` → **최신 회차** 당첨번호
- `GET /api/draw?round=1178` → **특정 회차** 당첨번호

```jsonc
{
  "ok": true,
  "data": {
    "round": 1178,                        // 회차 번호
    "date": "2025-06-28",                 // 추첨일
    "numbers": [5, 6, 11, 27, 43, 44],    // 당첨번호 6개, 오름차순
    "bonus": 17,                          // 보너스 번호 1개
    "firstPrize": {                       // 1등 당첨금 정보 (사장 결정으로 추가)
      "winners": 12,                      // 1등 당첨자 수 — 0명인 회차도 실제로 있음(예: 1회차)
      "amountPerWinner": 2391608407       // 1등 1인당 당첨금(원). 표시 형식(예: "23억 9,160만원")은 프론트가 정함
    }
  }
}
```

- **당첨확인 탭 사용법**: 탭 열 때 `GET /api/draw`(파라미터 없이)로 최신 회차 번호를 알아내서 회차 chip 목록을 그리고, 사용자가 chip을 고르면 `?round=`로 그 회차를 가져온다. 회차는 1부터 최신까지 빠짐없이 이어지므로 최신 회차 번호 하나면 chip 목록을 만들 수 있다.
- **등수 계산은 프론트 몫**: 서버는 당첨번호·보너스·1등 당첨금 정보를 주고, "몇 개 맞았는지·몇 등인지"는 화면에서 계산한다. (규칙: 6개=1등 / 5개+보너스=2등 / 5개=3등 / 4개=4등 / 3개=5등 / 그 외 낙첨.)

### 함수 2 — `GET /api/stats` (전체 회차 통계)

- `GET /api/stats` → 1회차부터 최신 회차까지 전부 집계한 결과

```jsonc
{
  "ok": true,
  "data": {
    "latestRound": 1231,                  // "1231회차 기준" 표시용
    "frequency": [                        // 번호별 출현 횟수 — 정확히 45개, 번호 순
      { "number": 1, "count": 169 },
      { "number": 2, "count": 154 }
      // ... 45번까지
    ],
    "oddEven": { "odd": 3780, "even": 3606 },   // 전체 회차에서 나온 홀수/짝수 개수
    "mostFrequent":  [                          // 자주 나온 번호 — 정확히 3개
      { "number": 34, "count": 184 },
      { "number": 27, "count": 181 },
      { "number": 13, "count": 179 }
    ],
    "leastFrequent": [                          // 드물게 나온 번호 — 정확히 3개
      { "number": 9,  "count": 136 },
      { "number": 22, "count": 144 },            // 22번과 32번이 144회 동률 → 낮은 번호 우선
      { "number": 32, "count": 144 }
    ]
  }
}
```

- 집계는 **본번호 6개만** 대상이고 보너스 번호는 뺀다. (사장 결정으로 **확정** — 2026-07-07)
- `mostFrequent`/`leastFrequent`는 서버가 미리 골라준다. **동률이면 번호가 낮은 쪽을 앞에** 둔다(양쪽이 같은 규칙을 각자 구현하다 어긋나는 걸 막기 위해 서버에서 한 번만 계산).
- 통계 화면의 "번호별 출현 빈도 45줄"과 홀짝 막대는 `frequency`와 `oddEven`으로 그리면 된다.

### 캐싱 방침 (Phase 2 구현 시 적용 — 참고용)

- 지나간 회차는 결과가 안 바뀌므로 오래 캐싱, 최신 회차·통계는 짧게(시간 단위) 캐싱. 동행복권에는 필요한 만큼만 요청한다. 프론트가 신경 쓸 건 없음 — 그냥 부르면 된다.

# Phase 2 구현 보고 (2026-07-07)

## 한 일 — 서버 함수 구현 완료

계약 v1.2 그대로 `/api/draw`, `/api/stats`를 구현하고 로컬에서 전부 검증했다.

### 만든 파일 (전부 `api/` 안)

| 파일 | 역할 |
|---|---|
| `api/draw.js` | `GET /api/draw`(최신) / `GET /api/draw?round=N`(특정 회차) |
| `api/stats.js` | `GET /api/stats` — 전 회차 집계 (본번호만, 자주/드문 3개씩) |
| `api/_lib/dhlottery.js` | 동행복권 호출·데이터 변환·최신 회차 탐지 |
| `api/_lib/draws.js` | 스냅샷 + 실시간 병합 저장고, 메모리 캐싱 |
| `api/_lib/http.js` | 응답 겉봉투(`ok`/`error`) 헬퍼 |
| `api/_data/draws-snapshot.json` | **전 회차(1~1231회) 스냅샷** (160KB, 코드에 포함) |
| `api/_scripts/build-snapshot.js` | 스냅샷 (재)생성 스크립트 — `node api/_scripts/build-snapshot.js` |

(`_`로 시작하는 폴더는 Vercel이 URL로 노출하지 않는다 — 내부 전용.)

### 중요한 발견 — 동행복권 API가 바뀌어 있었다

- 널리 알려진 옛 JSON 주소(`common.do?method=getLottoNumber`)는 **2026년 사이트 개편으로 사라졌다** (무조건 첫 화면으로 돌려보냄).
- 새 결과 페이지가 쓰는 내부 주소를 찾아냈다: `GET /lt645/selectPstLt645InfoNew.do?srchDir=center&srchLtEpsd=<회차>`
  - 한 번 부르면 요청 회차 주변 **10개 회차 묶음**을 준다. 덕분에 전 회차 수집이 1,231번이 아니라 **124번** 요청으로 끝났다(예의 항목 충족).
  - 회차·당첨번호 6개·보너스·추첨일·1등 당첨자수/1인당 금액이 다 들어있어 계약 그대로 채울 수 있다.
- "최신 회차"를 직접 알려주는 주소는 없어서, **날짜 기반 추정(매주 토요일 추첨) + 실제 조회로 확인**하는 방식으로 구현했다. 오늘 검증: 추정 1231회 = 실제 1231회(2026-07-04) 정확히 일치.

### 캐싱 (예의 + 속도)

- **스냅샷**: 지나간 회차는 결과가 안 바뀌므로 1~1231회를 파일로 코드에 포함. 평상시 동행복권 요청은 "최신 회차 확인" 수준으로만 나간다. DB 아님 — 그냥 정적 파일.
- **스냅샷이 오래되면**: 서버가 부족한 회차만 묶음 단위로 실시간으로 받아와 메모리에 채운다. 배포 후 몇 주 지나도 알아서 최신을 유지. 가끔(배포 전에 한 번) 스냅샷 스크립트를 다시 돌려주면 더 좋다.
- **CDN 캐시 헤더**: 과거 회차 30일 / 최신 회차 10분 / 통계 1시간(+하루 동안 이전 값 보여주며 갱신). 메모리에도 최신 회차 번호를 10분 캐싱.

## 확인한 것 — "app/ 화면 + api/ 함수가 한 주소에서 같이 동작"

- `vercel` CLI가 이 컴퓨터에 없고, `vercel dev`는 브라우저 로그인이 필요해서 대신 **vercel.json과 동일한 규칙의 로컬 서버**(정적 파일은 `app/`에서, `/api/*`는 함수 호출)를 띄워 검증했다 (사장이 허용한 "동등한 방법"):
  - `GET /` → 200, `<title>로또 드로우</title>` 정상 로드
  - `app/`의 CSS 5개·JS 6개 전부 200
  - 같은 주소에서 `GET /api/draw` → 최신 1231회, `?round=1178` → 실제 당첨번호 일치, `/api/stats` → frequency 45개
- 즉 화면과 데이터가 한 주소에서 함께 동작하고, 이 구조 그대로 Vercel에 올리면 된다. **실제 Vercel 위에서의 최종 확인은 첫 배포 때 아래 체크리스트로** 하면 된다. (진짜 `vercel dev`를 원하면 사장 터미널에서 `! npx vercel login` 후 `! npx vercel dev`.)

## 프론트 제안 계약에 대한 회신 (report-front.md의 "제안하는 데이터 계약" 관련)

프론트가 제안한 `GET /api/rounds`(배열)·`GET /api/stats`(맨숫자 45칸)는 **v1.2로 대체**됐다 (검수 지적과 동일). 전환할 때 대응표:

| 프론트가 기대하던 것 | v1.2에서는 |
|---|---|
| `GET /api/rounds` 최신순 배열 | `GET /api/draw`(파라미터 없음)로 최신 회차 번호를 얻고, chip은 그 번호에서 최근 5개 생성. 각 회차 상세는 `GET /api/draw?round=N` |
| 필드 `nums` | `numbers` |
| 날짜 `"2024.06.29"` | `"2024-06-29"` (YYYY-MM-DD) |
| 겉봉투 없음 | 모든 응답이 `{ ok, data }` / `{ ok: false, error: { code, message } }` — `error.message`는 그대로 화면에 보여줘도 되는 한국어 |
| stats 45칸 맨배열 + 자체 계산 | `frequency`(객체 45개) + `oddEven`/`mostFrequent`/`leastFrequent`/`latestRound`를 서버가 계산해서 줌. **자주/드문·홀짝은 자체 계산하지 말 것** (동률 규칙 어긋남이 실데이터에서 실증됨: 22·32번 144회 동률) |
| (없었음) | `firstPrize` { winners, amountPerWinner(원) } — 결과 카드에 표시(사장 결정). **winners가 0인 회차가 실제 14번 있으니** 그 경우 표시도 정할 것 |

상단 바 "제 1128회" mock 라벨도 `GET /api/draw`의 `round`로 교체하면 된다. 그 밖에 막히는 게 있으면 `report-front.md`에 질문 남겨줘 — 바로 회신한다.
